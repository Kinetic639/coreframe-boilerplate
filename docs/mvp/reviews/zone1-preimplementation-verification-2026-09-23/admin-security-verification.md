**Is `org_owner` technically a protected role today?** **Partially, and misleadingly so.** The role _definition_ is protected (immutable, can't be deleted). The _assignment_ of org_owner to a user — the operation the product contract actually cares about — is governed by the same generic `members.manage` (or even `invites.create`) permission as any other role, with zero ownership special-casing. **In the sense the contract means, org_owner is NOT protected today.**

## Part 2 — Privilege escalation

| Path                                       | Actor's own authority compared to the grant before persisting?                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Create custom role with chosen permissions | **No** — gated only on `members.manage`; nothing inspects the actor's own permission set                  |
| Edit existing custom role's permissions    | **No** — same gap                                                                                         |
| Assign org-scoped role to a user           | **No** — same gap                                                                                         |
| Assign branch-scoped role to a user        | **No** for actor-vs-grant comparison, but scope containment is architecturally sound (see vector 4 below) |
| Grant/revoke `org_owner`                   | No owner-only gate exists at all (Part 1)                                                                 |

**Escalation vectors — concrete findings:**

1. **Can an actor grant THEMSELVES broader permissions than they currently hold?** → **CONFIRMED VULNERABILITY.** A `members.manage`-only admin can create a role containing any permission slug (including wildcards like `org.*`/`members.*`) and assign it to themselves — nothing compares the new role's permission set against the actor's own compiled effective permissions.
2. **Can an actor grant ANOTHER person broader permissions than the actor's own authority?** → **CONFIRMED VULNERABILITY**, identical evidence — the code path doesn't distinguish self vs. other target.
3. **Can an actor create a role with permissions they don't hold, then assign it?** → **CONFIRMED VULNERABILITY** — role-permission insertion is gated only on `members.manage`, never checked as a subset of the actor's own permissions.
4. **Can branch-scoped role management escape into org-wide permissions?** → **SAFE.** Live-verified: branch-scope compiled permissions always carry a non-NULL `branch_id`; the org-wide permission check function explicitly requires `branch_id IS NULL`. No wildcard-driven escape found — this is the one architecturally sound axis.
5. **Can `org_owner` be granted by a path other than an owner-only route?** → **CONFIRMED VULNERABILITY, doubly so** — no owner-only path exists at all, AND a second, independently weaker route exists via invitations: `invites.create` alone (a permission distinct from and weaker than `members.manage`) is sufficient to mint a new `org_owner`, since the `SECURITY DEFINER` acceptance RPC copies invitation role-assignments in with zero re-check of the original inviter's own authorization.

## Part 3 — Invitation / one-organization invariant

1. **Creation-time conflict check**: YES, implemented and working. The live eligibility RPC checks self-invite, already-a-member, duplicate-pending-invite, and `ALREADY_IN_ORG` (member of any OTHER active org, by email match) BEFORE the invitation is created.
2. **Acceptance-time re-validation**: **MISSING — confirmed gap.** The live acceptance RPC (full body inspected) validates only auth/pending/expiry/email-match — it does NOT re-check the one-org invariant, and unconditionally upserts membership. If a user joins a different org between invite-creation and acceptance, nothing stops them from ALSO joining the original org. No DB-level constraint enforces "one active org per user" globally either (only a per-org duplicate-row constraint).
3. **Transactional safety**: **Safe.** The entire accept flow runs inside one PL/pgSQL function with an implicit savepoint — any error rolls back all writes from that invocation, no half-created membership possible.
4. **Both org-scoped and branch-scoped assignments created correctly on acceptance?** Yes, confirmed via live function body.

**PITCH vs PILOT**: item 1 (creation-time check) is PITCH-relevant, live, and will visibly work in any demo invitation flow. Item 2 (acceptance-time gap) is PILOT-relevant only unless the demo specifically stages the exact race condition — not something a standard walkthrough would trigger.

## Part 4 — Member removal / revocation / historical identity

1. **What's revoked, Auth identity preserved?** Confirmed: soft-deletes membership + all org/branch role assignments; Auth identity (`auth.users`/`public.users`) is never touched — zero `deleteUser` calls found anywhere.
2. **Loses authorization on the very next request?** **Yes, confirmed via a live, synchronous trigger chain** — membership soft-delete immediately triggers deletion of the user's compiled `user_effective_permissions` rows for that org, in the same transaction. All server-side authorization (RLS and app-layer) reads this table fresh, never a JWT claim, for actual DB operations. The only stale artifact is a JWT-decoded role-display array used purely for UI badges, explicitly documented in the code as "NOT a database security issue" — matches the product contract's own accepted tolerance exactly.
3. **Historical authorship survives removal?** **Yes, survives intact — by construction.** Since removal never deletes the underlying user row, none of the `created_by`/`actor_id` foreign keys are ever triggered. **Latent gap disclosed for completeness**: several of these FKs are `ON DELETE SET NULL` (inventory movements, audit/activity log, some ticket-activity fields) rather than `RESTRICT` — this would only matter if a full user-row hard-delete were ever implemented (it isn't today; no such code path exists), but is worth noting as a design consideration if that ever changes.
4. **Removed user's active-branch/session state**: not deeply investigated per the low-priority note in the task. Given the synchronous permission-recompilation guarantee (item 2), the removed user's session would simply start failing RLS-gated queries on their next request — no special force-logout/branch-reassignment code was found, but none appears necessary.

## Summary of the most critical findings

- **No owner-only gate exists anywhere** for granting/revoking `org_owner` — at the app, RLS, or DB-trigger level.
- **A second, weaker escalation path exists via invitations** — `invites.create` alone is sufficient to mint a new `org_owner`.
- **No last-owner-count protection exists at any layer** — removal, revocation, and self-demotion can all zero out an org's owners today.
- **No anti-privilege-escalation logic exists anywhere in role management** — every gate is "does the actor hold this one named permission," never "is what's being granted a subset of what the actor holds." Branch-scope containment is the one architecturally sound exception.
- **Invitation acceptance does not re-validate the one-org-per-user invariant** — creation-time check works; acceptance-time defense-in-depth is absent.
- **Member removal, revocation, and historical-identity preservation are all correctly implemented and solid** — this part of the system needs no fix.
