# Zone 3 — Phase 10C: Container Orchestration (Allocation → Container) — External Review Context

**Baseline:** `620bf2001e9d2aa9dea4e6933f9e0283cb53c1b3` ("phase10b"), confirmed clean via `git status` before this phase began. Phase 10B (including its own external-review-driven domain-integrity correction) is accepted, final, and untouched by this pass.

**Scope:** net-new physical container orchestration — `AllocationLine → one or more Containers`, explicit non-1:1 cardinality both directions, exact quantity conservation, org/branch isolation, RepairOrder ownership at the container-header level via the existing generic `reference_type`/`reference_id` pattern (`reference_type='repair_order'`). No UI. No Phase 10D (QR)/10E (relocation)/10F (issue) work. No Zone 5 integration.

## What already existed vs. what is net-new

`inventory_containers`/`inventory_container_lines` tables already existed (from an earlier, unrelated phase of this codebase) with **zero RPCs** — only RLS-gated direct table access. The container-workflow audit this project's plan was originally built from claimed "no application code currently writes to these tables." **That claim was live-verified WRONG**: `apps/web/src/app/actions/warehouse/ambra-location-inventory.ts` contains real, permission-gated, working write actions (`createLocationContainerAction`/`addItemsToContainerAction`/`removeItemFromContainerAction`/`relocateContainerAction`) — but a repo-wide grep confirmed **zero `.tsx`/hook files reference any of them**, so they are dead code from a UI standpoint today. Their own "allocation" concept directly mutates `inventory_balances.allocated_quantity` on every container add/remove — a fundamentally different, incompatible model from Phase 10C's own (which treats containers as pure physical grouping of stock already allocated via the real `inventory_create_allocation` RPC, never touching balance quantities). **Decision: preserved unchanged**, not migrated, not broken — reconciling the two models was judged out of this phase's scope and is disclosed here as a residual risk for whoever eventually builds UI on top of either path.

Net-new this phase: the `'empty'` container status value, 2 composite unique indexes (a live-discovered FK prerequisite), the `inventory_allocation_container_links` table, and 4 `SECURITY DEFINER` RPCs (`inventory_create_container`, `inventory_add_to_container`, `inventory_remove_from_container`, `inventory_seal_container`). See `migration-summary.md` for full DDL/RPC bodies and rationale.

## Known, disclosed limitations (updated post-correction)

1. **Concurrency is now genuinely proven, not merely reasoned about.** A real two-PostgreSQL-connection test (see `migration-summary.md`'s own "Genuine two-connection concurrency proof" section for full methodology) demonstrated actual row-lock blocking: Session B's own placement call blocked for ~3.13 seconds and resumed within 3ms of Session A's commit, then correctly failed once unblocked (6+6=12 exceeds the 10-unit cap). Final active link sum stayed at exactly 6, no orphan rows, no deadlock. This supersedes the original pass's own sequential-only disclosure for the specific scenario tested (same allocation line, two different target containers); the "same allocation, same container" variant remains reasoned-as-equivalent rather than separately re-run (see `migration-summary.md` for why).
2. **The pre-existing `ambra-location-inventory.ts` write actions remain semantically incompatible with the new engine** and were left untouched, not reconciled — unchanged from the original disclosure. Now additionally confirmed (T41-T42) that the new RESTRICTIVE RLS policies do NOT affect this legacy path, since it only ever writes to GENERIC (non-RepairOrder-owned) containers.
3. **`inventory_containers`/`inventory_container_lines`'s own pre-existing PERMISSIVE `_manage` policy is still present, unchanged** — but it is no longer the whole story: for RepairOrder-owned rows specifically, 6 new RESTRICTIVE policies now AND on top of it, closing the raw-write gap the original pass had left open (see finding #3 below). Generic (non-RepairOrder) containers/lines remain exactly as permissive as before.
4. **A real, pre-existing, intermittent connection-pooler session-state artifact was discovered** while re-verifying 097/098/099 via direct `psql` (unrelated to Phase 10C's own schema/RPCs — it guards `inventory_balances` via a completely different, pre-existing trigger and GUC). Disclosed in full in `migration-summary.md`. Does not affect MCP's own `execute_sql` connection path, which is this project's primary, authoritative execution path.

## Correction pass (2026-09-14, same-day external review)

External review of the accepted Phase 10C architecture found four gaps. All four were verified live before any fix (per explicit instruction not to assume the reviewer correct), and all four were confirmed real:

1. **Allocation-location vs. container-location invariant — CONFIRMED, fixed.** `inventory_add_to_container` never required `allocation_line.location_id = container.current_location_id`; live-verified via `pg_get_functiondef` before any change that the container's own `current_location_id` wasn't even selected. Fixed: the RPC now rejects a mismatch (`22023`) before any mutation. New pgTAP T11-T14.
2. **Cross-RepairOrder container-mixing — CONFIRMED, fixed.** The original T11-T13 scenario proved cross-RepairOrder mixing as a SUCCESS case. Fixed: when a container declares `reference_type='repair_order'`, the RPC now resolves the placing allocation's own RepairOrder via the accepted chain and rejects a mismatch (`P0002`, exact UUID identity, never SKU). Same-RepairOrder multi-allocation-line placement remains fully supported — cardinality unchanged. New pgTAP T15-T21 replace the old T11-T13.
3. **Raw-write bypass on `inventory_containers`/`inventory_container_lines` — CONFIRMED, fixed narrowly.** Live-verified their own pre-existing RLS is a single PERMISSIVE `ALL`-command policy gated only on `.operate`, no ownership-awareness. Fixed: 6 new RESTRICTIVE policies deny direct authenticated DML on RepairOrder-owned rows only; generic containers are provably unaffected (T41-T42); the 4 canonical RPCs are provably unaffected (`rolbypassrls=true` on `postgres`/`service_role`, live-verified via `pg_roles`).
4. **Missing genuine concurrency proof — CONFIRMED gap, now closed.** See "Known, disclosed limitations" item 1 above and `migration-summary.md` for the full methodology and measured result.

`RepairOrdersService`'s own application-layer ownership checks were kept, unchanged, as deliberate defense-in-depth alongside the new DB-level checks — not removed merely because the RPC now also enforces the invariant.

`inventory_create_container`'s own generic reference-validation question (should it verify a `reference_type='repair_order'` reference resolves to a real RepairOrder?) was evaluated and deliberately left unchanged — see `migration-summary.md` for the full reasoning (the app-layer wrapper already validates existence before ever calling the RPC, and the new placement-time ownership check independently renders a fabricated reference inert).

No Phase 10D/10E/10F work was started. Zone 5 was not touched. No Phase 10C migration was edited in place — both fixes are new, forward migrations.

## External review questions (28 original + 6 from the correction pass = 34)

1. Is the quantity-conservation invariant (`SUM(active link quantity) <= allocation_line.allocated_quantity`) actually race-safe, or does the row-locking strategy (lock container, then lock the allocation_line, then read the sum) leave a window where two concurrent `inventory_add_to_container` calls against the _same_ allocation line could both pass the check? Walk through the lock acquisition order in `inventory_add_to_container`'s own body and confirm whether it is sufficient.
2. Is locking the container row _before_ the allocation_line row (rather than the reverse, or locking only the allocation_line) correct, and does this ordering hold consistently across all three write RPCs (`add`, `remove`, and indirectly `seal`) such that no cross-function deadlock cycle is possible?
3. Given concurrency could not be tested with real concurrent sessions, is the lock-ordering argument in `migration-summary.md` and the pgTAP header comment convincing on inspection alone, or does it need a genuine multi-connection test before this can be trusted in production?
4. Does the decision to derive variant/location/lot/serial for a container line entirely from the allocation line's own row (never accepting them as separate RPC input) correctly prevent a caller from placing stock of the wrong variant into a container, and is this consistent with the Phase 10B precedent it claims to follow?
5. Is the `inventory_allocation_container_links` table's write boundary actually closed? Specifically: does the `INSERT ... WITH CHECK (false)` policy plus the total absence of an `UPDATE`/`DELETE` policy under `FORCE ROW LEVEL SECURITY` genuinely deny all four DML commands to the `authenticated` role, or is there a gap (e.g. does `FORCE RLS` actually apply to the table owner in a way that matters here, or could `service_role` reach this table unexpectedly)?
6. T22 in the new pgTAP suite proves a raw `INSERT` is denied. Should there also have been an explicit raw-`UPDATE`/raw-`DELETE` attempt test, given no policy exists for those commands at all — or is proving `INSERT` denial sufficient given the RPCs are the only place `UPDATE`/`DELETE` semantics on this table are exercised?
7. Is preserving `apps/web/src/app/actions/warehouse/ambra-location-inventory.ts` unchanged (rather than deleting it, gating it, or reconciling its model with the new engine) the right call, given it is real, permission-gated, callable code that — if ever wired to UI — would silently corrupt `inventory_balances.allocated_quantity` in a way the new Phase 10C engine does not expect or reconcile with?
8. Should a follow-up task (even if out of Phase 10C's own scope) be opened now to track the `ambra-location-inventory.ts` incompatibility, rather than leaving it as a footnote in this bundle only?
9. Is leaving `inventory_containers`/`inventory_container_lines`'s own pre-existing, broader RLS policy (gated only on `.operate`, no semantic validation) untouched an acceptable scope boundary, or does it constitute a live, exploitable gap that should have been closed in this phase regardless of the pre-existing actions that depend on it?
10. Does the composite-FK prerequisite (`ON DELETE RESTRICT` from the new link table to both `inventory_allocation_lines` and `inventory_container_lines`) correctly prevent an allocation line or container line from ever being hard-deleted while an active OR soft-deleted link still references it — and is `RESTRICT` (versus `CASCADE` or `SET NULL`) actually the right choice here for preserving placement history?
11. Was the discovery that neither `inventory_allocation_lines` nor `inventory_container_lines` had a composite `(id, organization_id, branch_id)` unique index handled correctly — are the two new indexes actually necessary and sufficient, and do they introduce any risk (e.g. uniqueness violation on existing data) that should have been checked before applying?
12. Is the empty-status transition logic correct in all directions: does a container correctly move `empty → active` on first placement, stay `active` while ANY of its own content remains (even if one specific allocation line's own contribution was fully removed), and correctly move back to `active → empty` only when its TOTAL active content reaches exactly zero (never when just one line is emptied)?
13. Does the empty-status logic correctly avoid reviving an `archived` container — i.e., is `status <> 'archived'` actually checked before the auto-transition to `'empty'` fires on a full-removal event, and is this the right rule (should a sealed container behave differently on full removal too)?
14. Is `inventory_create_container` starting a new container at `status='empty'` (rather than `'active'`) the right default, and does every downstream consumer (the RPCs, the service wrapper, and any future UI) correctly treat `'empty'` as equivalent to "open for placement," matching `'active'`?
15. Was the decision to omit `inventory_close_container` (on the grounds that `add`/`remove` already own the empty-status invariant atomically) correct, or is there a real use case this phase overlooked — e.g. force-archiving a container that still holds stock — that a close RPC would have been needed for?
16. Does `RepairOrdersService.placeAllocationInContainer`'s ownership chain actually prevent a caller from placing an allocation line belonging to a DIFFERENT RepairOrderLine (even one the caller has legitimate access to) into a container? Walk through `listAllocationsForLine`'s own filtering and confirm the `.some(l => l.id === input.allocationLineId)` check is sufficient.
17. Does the container-ownership check in `placeAllocationInContainer` (matching `reference_type==='repair_order'` and `reference_id===scope.repairOrderId`) correctly reject placement into a container that belongs to a DIFFERENT RepairOrder, or one with no RepairOrder reference at all (e.g. one created directly via the pre-existing `ambra-location-inventory.ts` actions)?
18. Does `removeAllocationFromContainer`'s ownership chain (link must belong to one of this RepairOrderLine's own valid allocation lines) correctly prevent removing a link that happens to sit in the same container but belongs to an unrelated RepairOrderLine's own allocation?
19. `inventory_containers.reference_id` is `text`, not `uuid` (unlike reservations'/allocations' own `uuid` columns). Does every place this value is compared (in the RPC, in the service, in tests) correctly account for this type difference, with no silent cast or comparison bug?
20. Is `inventory_containers.current_location_id`'s `NOT NULL` + composite FK to `warehouse_locations` combined with the `can_store_inventory` check in `inventory_create_container` sufficient to prevent a container from ever being created at a non-stockable or cross-branch location?
21. For the multi-container-split scenario (one allocation line's 10 units split 6+4 across two containers, T4-T8): does the pgTAP suite actually prove independence of the two containers' own contents, or could a bug that conflates them still pass these specific assertions?
22. For the multi-allocation-line-per-container scenario (T11-T13, two different RepairOrders' own allocations sharing one physical container because they happen to share a SKU): is this actually a desired, correct outcome of the design, or does it represent an unintended cross-RepairOrder data-mixing risk that the RepairOrder-ownership wrapper doesn't fully account for at the container level (since one container can legitimately hold stock "belonging to" two different RepairOrders simultaneously)?
23. Given #22, does a container's own `reference_type`/`reference_id` (set once, at creation, to a single RepairOrder) still make sense as "the" owner of a container that can, in practice, hold placements from multiple unrelated RepairOrders' own allocations? Should the service wrapper's own container-ownership check in #17 be revisited in light of this?
24. Are the T15a-e assertions (allocation/reservation `fulfilled_quantity` and all three balance quantities unchanged by container placement/removal) actually exhaustive, or is there another balance-adjacent column (e.g. any future `container_reserved_quantity`-style field) that should also have been checked?
25. Is the actor-identity + `has_branch_permission(..., 'warehouse.inventory.operate')` gating on all 4 RPCs the correct permission granularity, or should container operations have their own, more specific permission slug distinct from general inventory operate (especially given RepairOrder-scoped container work is conceptually a Workshop-module operation, not a general Warehouse one)?
26. Do the 3 new server actions (`createRepairOrderContainerAction`/`placeAllocationInContainerAction`/`removeAllocationFromContainerAction`), gated only on `WAREHOUSE_INVENTORY_OPERATE`, correctly match the permission model the underlying RPCs themselves enforce, with no privilege mismatch between the action layer and the RPC layer?
27. Is the 3-event audit/Mode-A decision (`container_created`, `stock_placed_in_container`, `stock_removed_from_container`) complete, or should a `container_sealed` event also have been added given `inventory_seal_container` is a real, wrapper-reachable... actually NOT wrapper-reachable (no service method wraps `inventory_seal_container` yet) — is that omission itself correct for this phase's scope, or a gap?
28. Taken as a whole, does this phase's own boundary-drawing (build the engine + a RepairOrder-facing service wrapper for create/place/remove only, explicitly NOT wrapping `inventory_seal_container`, explicitly NOT building UI, explicitly NOT reconciling the pre-existing dead-code writer) represent a coherent, minimal, correctly-scoped unit of work — or does it leave the container feature in a state that will require significant rework once Phase 10D (QR) or later UI work actually needs to call `seal`?
