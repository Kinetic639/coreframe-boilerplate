### `inventory-movements-client.tsx` — the one conflict requiring real judgment, not a mechanical "take main"

Zone 1's original version deliberately split a LIVE `useAppStoreV2` read (feeding `DataView`'s own cache scope) from a separate, frozen SSR `activeBranchId` prop (feeding the detail panel unchanged) — a defensive measure against the DataView's cache going stale if the component stayed mounted across a branch change. Main's own independent version consolidated onto a single `activeBranchId` PROP, used identically for both purposes.

Verified before accepting main's simpler version: (1) main's own parallel Balances/Products consumers already use a single prop-based value successfully, establishing it as the accepted, working pattern elsewhere in main's own codebase; (2) neither Movements nor Balances/Products has a `key={branchId}`-based remount guarantee — so there's no asymmetry that would make Movements uniquely need the extra live-read complexity Balances/Products don't; (3) Zone 1 Phase 1's own branch-switch mechanism (`router.replace("/dashboard/start")` + `router.refresh()`) always navigates away from any warehouse detail page on switch, fully remounting it on next visit — the exact same-mounted-instance staleness scenario the original live read defended against does not occur under normal navigation. Conclusion: main's simpler design is not a regression; it was a reasoned decision, not a blind "main wins."
