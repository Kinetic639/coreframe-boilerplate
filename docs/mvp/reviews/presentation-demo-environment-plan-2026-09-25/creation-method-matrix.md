# Fixture Creation Method Matrix

Preference order per this task's own instruction: **A. Existing application UI → B. Existing server action/service → C. Existing seed/demo fixture tooling → D. Direct SQL (last resort, flagged, not executed)**.

**No dedicated seed/demo fixture tooling (Category C) was found in this repo.** A search for `*seed*` files outside `__tests__` found only migration-level DB seeds for permissions and movement-type catalog rows (`20260320000011_target_p3_b3_seed.sql`, `20260915155606_ic2_seed_reversal_document_movement_type.sql`, etc.) — none of these are demo-org/demo-data seeding tools. Category C is therefore unavailable for every fixture below; the realistic choice is always A or B.

## Direct SQL requirement: NONE identified

Every fixture in this plan has a real, existing, in-app UI path (Category A). **No fixture in this plan requires direct SQL.** If, during actual execution, any step turns out to need a capability the UI doesn't expose (e.g. a specific field only settable via a server action, or a role/permission combination the UI doesn't offer a picker for), that specific gap will be flagged explicitly for approval before falling back to Category B (an existing server action called directly, e.g. via a script) — Category D (raw SQL `INSERT`) is not expected to be needed anywhere in this plan and would require a fresh, specific approval if it ever became necessary.
