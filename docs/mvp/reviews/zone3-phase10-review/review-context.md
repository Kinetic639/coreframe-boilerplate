## F. Live Supabase schema findings (`repair_order_line_movement_links`)

Columns: `id, repair_order_line_id, inventory_movement_line_id, applied_quantity, relation_type, created_at` — no `organization_id`/`branch_id` of its own (Tier 1 join-derived scope, per the architecture doc). Constraints: PK; FK to `repair_order_lines` (`ON DELETE CASCADE`); FK to `inventory_movement_lines` (`ON DELETE CASCADE`); `CHECK (applied_quantity > 0)`; `CHECK (relation_type IN ('receipt','issue','reversal'))`; `UNIQUE (repair_order_line_id, inventory_movement_line_id, relation_type)`. RLS: FORCE RLS enabled; `_select` scoped through `repair_order_lines → repair_orders → has_branch_permission('workshop.repair_orders.read')`; `_insert` scoped through the same join but gated on `warehouse.inventory.operate` OR `.adjust`; `_delete_deny` (`qual = false`, unconditional) — no UPDATE policy at all, so the table is effectively insert+select-only, immutable once written. Row count live at start of this phase: **0**. `inventory_movement_lines` has 26 columns, no line-level provenance/reference column (REPO VERIFIED, matches the architecture doc's own prior finding) — attribution can only be layered on top via this separate link table, never inferred from a column on the movement line itself.

## G. Cardinality decision

Verified (not assumed) that the unique constraint's shape permits one `inventory_movement_line` to be split across multiple `RepairOrderLine`s (no 1:1 restriction in either direction). The new RPC therefore enforces the resulting invariant itself: `SUM(applied_quantity)` for one `inventory_movement_line_id`, across every `repair_order_line_id` and `relation_type` that references it, must never exceed that movement line's own `quantity`. This sum-check runs under a row lock (`SELECT ... FOR UPDATE OF iml`) taken on the movement line row before the sum is computed, serializing concurrent attribution attempts against the same movement line so the cap cannot be raced past by two simultaneous calls.

## H. Attribution validation rules implemented (all inside the new RPC)

Actor-identity match; `applied_quantity > 0`; `relation_type ∈ {receipt, issue}` (`reversal` rejected outright, see §N); RepairOrderLine exists and its RepairOrder's org/branch is resolved authoritatively (never trusting a client-supplied org/branch); actor holds `warehouse.inventory.operate` or `.adjust` in that branch; movement line exists (row-locked); movement line's own org/branch matches the RepairOrder's; movement is `status = 'posted'` (not draft/cancelled/reversed); `relation_type` matches the movement's real `inventory_movement_types.category`; if the movement header carries a `reference_type = 'repair_order'`, its `reference_id` must equal this RepairOrder; if the RepairOrderLine carries a `variant_id`, it must equal the movement line's own `variant_id` (skipped, not rejected, when the RepairOrderLine has no `variant_id` — "where authoritative data exists"); the cardinality cap from §G; duplicate `(repair_order_line_id, inventory_movement_line_id, relation_type)` rejected with a distinct domain error (23505), not a silent no-op and not a raw constraint-violation leak.

## I. RPC design and security hardening

`attach_repair_order_line_movement` — `SECURITY DEFINER`, `SET search_path = public, pg_temp` (hardened, prevents search-path-hijack attacks on a definer function). Actor-identity check is the FIRST statement after parameter validation, matching `materialize_repair_orders_from_session`'s own established pattern. `EXECUTE` revoked from `PUBLIC` and (via the corrective second migration, see `migration-summary.md`) from `anon` explicitly — LIVE VERIFIED to now match the two sibling RPCs' own grant shape exactly (`{postgres, authenticated, service_role}`, no `anon`). No client-trusted scope: org/branch are always resolved from the authoritative parent rows (`repair_orders`, `inventory_movement_headers`/`inventory_movement_lines`), never accepted as parameters. All domain errors use a specific ERRCODE with a stable, human-readable, already-safe message; any other error (a raw constraint violation, connection error, etc.) is not part of this RPC's own deliberate design and is caught by the service layer's normalizer, replaced with a generic message, and logged server-side in full (see §J).

## J. Error normalization

`normalizeMovementLinkRpcError` (service layer) — a 12-entry allowlist, each requiring BOTH the exact ERRCODE and a regex match against the RPC's own known, stable message shape (not errcode alone — several of these codes, e.g. 42501/22023, are broad Postgres error _classes_ a native, un-authored error could also raise; matching on errcode alone would have let such an error's raw, schema-revealing message pass through). Anything not matching both falls through to a single generic, safe message; the full raw error is always logged server-side first via `console.error`. This mirrors the exact hardening `normalizeMaterializationRpcError` already received during Phase 3/4's own corrective-review pass (Finding E).

## Q. Security/RLS — a disclosed, pre-existing residual gap

The Phase 2 `repair_order_line_movement_links_insert` RLS policy (permission-gated on `warehouse.inventory.operate`/`.adjust`) was **not** tightened or replaced by this phase.
