# Server-Action Analysis (Problem A: click → `changeBranch` resolves, observed 10–15 s)

## The model's gap

`changeBranch` alone is 13 serial Supabase calls, modeled at ~1.3–2 s transatlantic. That leaves **~8–13 s unexplained**. Dev compilation is excluded (this is a Vercel production build). The gap must come from time the action spends **not executing its own calls**, or from each call being much slower than modeled.

**Combined:** a realistic bad case adds up to 10–15 s. For example: the user focuses the window → a poll starts on a cold or transatlantic instance (~3–4 s) → the click queues behind it → `changeBranch` runs on another cold instance (~1.5 s init + ~2 s calls) → occasionally a token refresh adds a full render (~2.5 s). **No single hypothesis explains 10–15 s on its own.** H1+H2+H3 together do, and every one of them is _structural_, not accidental.

## Confidence

- H1: the mechanism is certain (verified in Next source, poll triggers verified in code). How much it contributes in UAT is unmeasured.
- H2/H3: the mechanism is certain given the defaults; the actual region and cold-start rate are unverified.
- H4: the mechanism is verified; how often it happens is unknown.
- H5: speculative.

## What this implies for the fix (independent of which hypothesis dominates)

1. **Take the switch out of contention.** No background server action should sit ahead of a user-initiated switch:
   - background reads (poll, permission sync) should not use the router's action queue at all;
   - or at minimum the poll must be suppressed while a switch is pending, and must not fire on focus immediately before one;
   - `PermissionsSync` should be seeded from the SSR snapshot so it doesn't fire on mount.
2. **Make the action cheap and close to the data.** Functions go in the Supabase region. The authorization context keeps its semantics (`getUser` + `loadDashboardContextV2` + `isBranchAccessible`), but with one `getUser` per request and independent reads in parallel.
3. **Don't let the action be followed by two more requests** (see `navigation-architecture-analysis.md`).
