# Adversarial Review of the Chosen Design

Each attack is followed by the response, and by what (if anything) the design changes because of it.

| #   | Attack                                                                                                                                                                   | Response                                                                                                                                                                                                                                                                                                                              | Design consequence                                                                                                             |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1   | "You never explained the 10–15 s. You are designing around hypotheses."                                                                                                  | Correct: no single hypothesis explains it. But every ranked cause (queue wait, cold starts, transatlantic latency, token-refresh re-render, slow Auth) is a function of _number of serial calls × per-call cost + things ahead in the queue_. Stages 1–4 cut each factor. No plausible cause is left untouched except an unknown one. | Stage 0 is a **gate**: if the measurement shows a cause outside H1–H5, stop and re-decide before Stage 3                       |
| 2   | "`redirect()` in a server action might not keep `isPending` true until the new tree commits, so the UI flickers or the toast fires early."                               | Real risk. The success signal is deliberately **not** tied to the action promise. It fires from the providers' hydration effect when the B context commits, so it is correct even if `isPending` ends early. The pending UI is kept by the switcher's own state until that signal.                                                    | Pending state = local state cleared by the commit signal (or failure), not `isPending` alone                                   |
| 3   | "On Vercel the redirect's internal fetch goes back out through the edge and the proxy. That's another hop and a possible cold start, so maybe no faster than `replace`." | It still removes one client↔function round trip **and one full render** (the page-only render). Worst case (streaming fails) Next falls back to a client navigation that renders once. Never worse than today's two renders.                                                                                                          | Measure the redirect path in Stage 0/3. ALT-3 is the fallback if the internal fetch is unreliable (e.g. Deployment Protection) |
| 4   | "The `?switched=` parameter is client-controlled input on an authorization-adjacent path."                                                                               | It is never authorization. It only lets the client prefer the **server-rendered** `activeBranchId` over its own sessionStorage, and only when they are equal. A forged value that isn't equal is ignored. A forged value that is equal is a no-op, because the server already says that branch.                                       | Compare against `context.app.activeBranchId` only; strip after use                                                             |
| 5   | "Dropping the early `setActiveBranch` breaks the per-tab sessionStorage override: the tab flips back to A."                                                              | Correct. This is the trap that a naïve "just redirect" implementation would hit (`_providers.tsx:55-89`).                                                                                                                                                                                                                             | R5 handshake is mandatory; a dedicated test ("after switch, a stale session entry A doesn't override server B")                |
| 6   | "Redirect target from the client is an open redirect."                                                                                                                   | The target is a **server-side allowlisted route key**, not a URL. Query params (e.g. `selected`) are validated (UUID) and are not authorization; the target page re-checks access.                                                                                                                                                    | Allowlist enum in the action                                                                                                   |
| 7   | "Moving to `dub1` might slow other things (US-hosted APIs, email, AI)."                                                                                                  | Plausible for some integrations. The dashboard critical path talks only to Supabase. Users are in Poland, so browser↔function also gets faster.                                                                                                                                                                                       | Stage 1 includes a check of outbound dependencies; the owner decides                                                           |
| 8   | "Request-scoped `getUser` caching weakens auth."                                                                                                                         | No: the same network validation, once per request, never reused across requests. The proxy's refresh-capable call stays. `getSession` stays banned for authorization.                                                                                                                                                                 | Tests: an invalid/expired JWT still fails in every loader/action                                                               |
| 9   | "Parallelizing loaders changes failure semantics (partial contexts, error ordering)."                                                                                    | Only independent reads are parallelized. Auth still gates everything. Each loader keeps its fail-closed return. The layout uses `allSettled` where today's code already degrades.                                                                                                                                                     | Zone 1 full regression suite + loader unit tests required for Stage 4                                                          |
| 10  | "Seeding `PermissionsSync` with SSR data can hide a permission change made in another session."                                                                          | Today's staleTime is already 5 min, and a full render reloads the snapshot from the DB. Seeding with the snapshot the same render just loaded is _fresher_ than a fetch queued behind other actions.                                                                                                                                  | None                                                                                                                           |
| 11  | "Poll suppression hides activity for a moment."                                                                                                                          | Suppressed only during a switch (seconds). The next poll or focus refreshes it.                                                                                                                                                                                                                                                       | None                                                                                                                           |
| 12  | "Two tabs: tab 1 switches while tab 2 is on A."                                                                                                                          | Unchanged: tab 2 keeps its sessionStorage working branch (existing design). The DB default changes as today.                                                                                                                                                                                                                          | None                                                                                                                           |
| 13  | "Why not ALT-3 (full document load)? It's simpler and bypasses the router entirely."                                                                                     | Hand-rolled CSRF on the only persistent switch, full-app rehydration, and lost UI state make it a worse default. It stays the documented fallback.                                                                                                                                                                                    | —                                                                                                                              |
| 14  | "The action succeeds but the redirect render fails (network drop). DB = B, screen = A."                                                                                  | Same class as today's post-action navigation failure. On the next load the tab's sessionStorage (A, accessible) keeps it consistently on A; the user can switch again. No mixed state is claimed as success, because no commit signal fires.                                                                                          | Show error/timeout toast if no commit within ~15 s                                                                             |
| 15  | "Stage 2 alone might be 'good enough' and Stage 3 unnecessary risk."                                                                                                     | Possible if Stage 1 lands. The design allows stopping after Stage 2 if Stage 0/after-Stage-2 measurements already meet GOOD. Stage 3 is justified mainly without co-location, or to reach GOOD robustly on cold instances.                                                                                                            | Re-measure after each stage; Stage 3 is conditional on targets not met                                                         |

## Residual risks accepted

- The Next.js internals behavior (redirect streaming) is verified in the 16.1.7 source but not yet on Vercel. It is covered by the fallback plus measurement.
- The region move depends on the owner. Without it, the demo target still needs Stages 2+3+4.
