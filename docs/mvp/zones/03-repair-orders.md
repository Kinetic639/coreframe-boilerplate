### Verified technical findings

Evidence classification used throughout: **LIVE VERIFIED** (confirmed via Supabase MCP against the live `supabase-target` project), **REPO VERIFIED** (confirmed from repository code/migrations), **HISTORICAL** (found only in archived/legacy material), **UNRESOLVED** (not yet provable).

**Workshop module — REPO VERIFIED, unchanged conclusion.** `apps/web/src/app/[locale]/dashboard/workshop/` is a pure auth/UI shell (4 files: `page.tsx` renders a static 6-card "coming soon" grid, `layout.tsx` only gates entitlement+permission, `loading.tsx`/`error.tsx` generic). `apps/web/src/modules/workshop/MODULE.md` explicitly scopes "Now" as shell-only and lists RepairOrder as "Future — not yet implemented." Zero domain tables, services, actions, or UI exist. This is a greenfield build, confirming the accepted historical audit's 🔴 NOT IMPLEMENTED verdict.

**Warehouse/workshop identifier (D3332/D3112-style code) — REPO VERIFIED, historical audit CONFIRMED, not contradicted.** The `D\d+` pattern in `parser_v4.ts` (`isBlockTitleLine` :477, tail-stripping :1213) is used exclusively as a discardable text/line-boundary marker in three call sites — never captured into any DTO or database field. `enhanced-delivery-pdf.tsx`'s `bodyShopCode` (:343-347) is a **synthetic, display-only** value computed from the last 3–5 digits of the order/ZW/WDD number with a literal `"D"` prefix — not read from source text, never persisted, zero other references repo-wide. **A live JSONB key literally named `warehouse_code` does exist** in `wdd_matcher_blocks.metadata` (present on 5,697 of the live blocks) — but this is a **different, unrelated concept**: a 3-digit "Magazyn" brand/section code (115/315/415/515 → VW/Skoda/Mirror/Seat via `WAREHOUSE_MAP`), confirmed identical in shape by both the live data and a repo test fixture (`wdd-matcher-movement-import-candidates.test.ts`: `warehouse_code: "115"`). **This is a field-name collision, not evidence that the D3332/D3112-style workshop context code is captured.** The product intent's desired warehouse/workshop context identifier does not exist anywhere today, live or in repo — it requires genuinely new parser work if it remains part of the business-identity design (see Open questions).

**Matcher session status lifecycle — REPO VERIFIED, matches LIVE CHECK constraint exactly.** Enum: `pending / processing / ready_for_review / approved / rejected / failed` (both `apps/web/src/lib/validations/wdd-matcher.ts:11-18` and live constraint `wdd_matcher_sessions_status_check`). Reachable transitions: `pending → processing` (`persistPreparedSessionAction`/`runMatchingAction`) → `ready_for_review` (automatic, via `updateMatchSummary`) or `→ failed` on any error. `rejected` is declared but never set by any code path. **`approved` exists in the schema and has exactly 1 live row, but `WddMatcherService.approveSession` (which sets `approved_by`/`approved_at`) has zero callers anywhere in the codebase** — no server action, no UI button. There is no `approveSessionAction`, `reviewBlockMatchAction`, or `bulkApproveExactLinesAction` wired up, even though the underlying service methods and Zod schemas exist. **The de-facto "ready" gate used by all downstream code today (`getMovementImportCandidates`, `listImportableSessionsForBranch`) is `ready_for_review`, not `approved`.**

**Source-line identity — REPO VERIFIED + LIVE VERIFIED: exists.** `wdd_matcher_lines.id` is a real, `gen_random_uuid()`-generated, stable UUID per source line — confirmed in both the live schema and the TypeScript DTO (`WddMatcherLine.id`). `line_number` is a block-relative array position (`index + 1`), not a durable source-document row number, and would shift if parsing logic reordered rows — use it only as a display ordinal. **Gotcha:** `persistPreparedSessionAction`'s `insertLines` call does not `.select()` the inserted rows back, so that one action's own in-memory return payload uses a synthetic `${blockId}-line-${arrayIndex}` id instead of the true DB UUID — any RepairOrderLine provenance mapping must read `wdd_matcher_lines.id` directly from the database (as the movement-import adapter already correctly does via `sourceLineId: line.id`, confirmed at `wdd-matcher.service.ts:551`), never from that action's synthetic payload.

**Advisor / CRM — REPO VERIFIED, conflicts with product intent §8 (see Product decisions).** `crm_contacts.linked_user_id` (nullable FK to `public.users`) exists and does let a CRM contact be linked to an app user — but `crm_party_roles.role` enum is `supplier/client/contractor/vendor/partner/receiver/payer/other`, with **no employee/staff/advisor value**. CRM's live architecture models the **customer/external-party** side (the vehicle owner), not internal staff. The only existing internal-staff-ownership analog in the codebase (`helpdesk_tickets.assigned_to` / `helpdesk_ticket_assignees.user_id`) references `public.users(id)` **directly**, with no CRM indirection at all. A legacy `public.contacts` table (2025-01) has an `'employee'` type but has no RLS and is not what `CrmContactsService` operates on — dead weight, not a real option.

**Generic attachments/comments — REPO VERIFIED + LIVE VERIFIED, matches prior audit, richer detail now available.** `app_attachments`/`app_comments`/`app_comment_events` all confirmed live with the exact shape described in the former Zone 9 audit. The full `CommentTargetDescriptor` interface and all three registry entries (`helpdesk.ticket`, `planning.task`, `planning.kanban_card`) were re-obtained verbatim, as was the complete, current `can_access_comment_target` SQL function body (from `20260605170000_planning_kanban_card_details.sql` — the latest of three migrations that progressively extend it; confirmed no later migration in either local tree redefines it). Both are exact templates for a future `workshop.repair_order` entry/branch — see Data and migration strategy.

**RLS tiering — LIVE VERIFIED, three distinct tiers exist today, matching Zone 1's documented gap.** Tier 1 (strongest — **FORCE RLS + branch-aware `has_branch_permission()`**): `inventory_movement_headers`, `inventory_reservations`, `crm_contacts`, `app_attachments`. Tier 2 (FORCE=false, org-only `has_permission()`, branch column present but unchecked): `helpdesk_tickets`, `helpdesk_ticket_assignees`, `app_comments`. Tier 3 (FORCE=false, org-only): `wdd_matcher_*`. **`has_permission(org_id, permission)` is structurally incapable of branch-scoped grants — its SQL body literally filters `AND branch_id IS NULL`.** `has_branch_permission(org_id, branch_id, permission)` is the correct, already-existing branch-aware helper. RepairOrder must be built to Tier 1, matching `inventory_movement_headers`/`crm_contacts`, not the weaker Help Desk/Matcher tiers.

**Advisor-ownership authorization template — REPO VERIFIED, exact code obtained.** `helpdesk_accept_ticket` (SECURITY DEFINER RPC, full body obtained) is the precise template for a RepairOrder claim/close/reopen RPC: re-derives org from the row (never trusts client input), checks manager-permission OR a per-row whitelist/assignee `EXISTS` check, guards against double-action via a state check, writes the state mutation and an activity-log row atomically in one function. Gotcha: even this template only checks org-level `has_permission`, not branch — a gap to deliberately not copy forward.

**Movement/reference architecture — LIVE VERIFIED + REPO VERIFIED.** `inventory_movement_headers.reference_type`/`reference_id` are free TEXT with no enum/CHECK constraint anywhere (confirmed both live and in migrations) — known values today are `"inventory_product"` and `"inventory_count"`. A new value (`"repair_order"` or similar) can be adopted with zero schema change to this mechanism. **Two parallel movement-posting engines exist**: the modern `InventoryMovementsService` (`inventory_create_draft`/`inventory_finalize_posting`/`inventory_create_and_finalize`/`inventory_save_draft`/`inventory_cancel_movement`, all confirmed live as SECURITY DEFINER RPCs taking explicit `p_actor_user_id`) used by `actions/warehouse/inventory/` and container relocation; and a legacy pair (`inventory_create_draft_movement`/`inventory_post_movement`) used only by `inventory-products.service.ts` for opening stock. RepairOrder integration must use the **modern** engine only.

**No `inventory_reverse_movement` function exists live.** Direct `pg_proc` search for `%reverse%` in the `public` schema returned zero results on the target project — this contradicts the archived former-Zone-18 audit's description of a working reversal RPC. That function does not exist on the authoritative project today (see Repository vs live-schema drift).

**Reservation/allocation and container infrastructure — LIVE VERIFIED + REPO VERIFIED: complete but fully dormant.** `inventory_reservations`/`inventory_reservation_lines`/`inventory_allocations`/`inventory_allocation_lines` exist live with full schema (reservation_number, status, `reference_type`/`reference_id`/`reference_number`, `expires_at`, priority). `InventoryEnterpriseService` has complete `createReservation`/`releaseReservation`/`createAllocation`/`releaseAllocation` methods, each with a matching server action. **Zero UI callers exist anywhere in the repository** for any of these four actions (confirmed by repo-wide grep) — this is architecture that was built ahead of need. The same is true of `inventory_containers`/`inventory_container_lines` (`createLocationContainerAction`, `addItemsToContainerAction`, `removeItemFromContainerAction`, `relocateContainerAction`, `findContainersByReferenceAction` — the last one already filters by `reference_type`/`reference_id`). This directly satisfies product intent §14 (reservation must remain possible): RepairOrder's data model, by using the same `reference_type`/`reference_id` pattern, will be immediately compatible with wiring this dormant system up later, with zero redesign.

**Movement-import adapter architecture — REPO VERIFIED, exact contract and full reference implementation obtained.** `MovementImportSourceAdapter` (`movement-import-adapters/types.ts`) is a clean, already-proven plug-in interface (`sourceType`, `loadSourceFields()`, `loadCanonicalDocuments()` returning `CanonicalMovementImportDocument[]`); `MovementImportSourceRegistry` is a simple array a new adapter appends itself to. The full 181-line `svwms-wdd-matcher.adapter.ts` reference implementation was obtained verbatim — it is the direct template for a future AutoStacja file-import adapter (product intent §16). This substantially de-risks that pilot requirement: it is a well-defined extension point in an already-generalized system, not a new subsystem to invent.

**Product/variant mapping — REPO VERIFIED.** `WarehouseImportResolverService.resolveVariant` does exact-normalized-token matching, then a stricter alnum-only "fingerprint" match, returning a tri-state result (`resolved`/`missing`/`ambiguous`). No fuzzy matching, no auto-create-on-demand — ambiguous/missing lines are surfaced as validation errors for a human to resolve in the UI. RepairOrderLine-to-catalog mapping should reuse this exact service rather than invent new resolution logic.

**Permission naming convention — REPO VERIFIED, exact constants obtained.** Pattern: `<module>.<resource>.<verb>` (lowercase, dot-separated) + `<module>.*` wildcard + `module.<module>.access` gate, all defined in `packages/contracts/src/permissions.ts`. Full Warehouse and full Help Desk permission constant lists were obtained verbatim. **Critically, Help Desk has no granular `update-own`/`update-all`/`assign`/`close`/`reopen` permission strings** — advisor-like ownership is enforced entirely in application code (`created_by === userId` checks layered on top of the coarse `READ`/`CREATE`/`MANAGE` triad), exact code quoted from `closeTicketAction`. This is the direct precedent for how RepairOrder's advisor-ownership-vs-manage-all model should be implemented.

**Domain-activity/audit infrastructure — REPO VERIFIED, decisive finding.** Two competing patterns coexist: a legacy per-module pattern (`helpdesk_ticket_activity`, `planning_task_activity` — each with different, bespoke column shapes) versus a newer, explicitly-mandated generic path: `platform_events` + `eventService.emit()`. The service file's own doc-comment states: _"This is the ONLY application-code path that may insert into `public.platform_events`. ... Direct inserts into `public.platform_events` from any other location are an architectural violation."_ The Warehouse module already uses this path exclusively for movement/product/location events. **RepairOrder must use this same path** — register new `actionKey`s (e.g. `repairorder.order.created`, `.assigned`, `.closed`, `.reopened`, `.identity_corrected`) in `event-registry.ts` with Zod metadata schemas, and call `eventService.emit()` from server actions. This directly satisfies product decision §39 (prefer domain activity + real inventory movement history, don't duplicate) — `platform_events` already is that mechanism.

### Final intended workflow

**Materialization (automatic path):** Matcher upload → parse → match → (recommended, pending product-owner sign-off per §18 above) a newly-built explicit "Approve session" action transitions `wdd_matcher_sessions.status` to `approved` → a new `materializeRepairOrdersFromSessionAction` reads all blocks/lines for that session, groups them by normalized business-identity key (org + branch + order_number + year — warehouse_code deferred per §4/§5), and for each group: looks up an existing `repair_orders` row by that key within the branch → if found, attaches a new `repair_order_source_documents` row + appends/updates `repair_order_lines`; if not found, creates a new `repair_orders` row + its lines + its first `repair_order_source_documents` row; if a conflicting-but-similar match is found (e.g. same order_number, different resolved VIN), the group is flagged `requires_resolution` and surfaced in a review UI rather than silently resolved either way → every create/attach/conflict emits a `platform_events` row via `eventService.emit()`.

**Manual path:** authorized user opens "New Repair Order" → fills header (order number, year, branch, optional VIN/warehouse code/brand/dealer, advisor) → system checks for a business-identity collision → creates the order (status `open`) → user adds lines manually (SKU/catalog lookup via `WarehouseImportResolverService`, quantity, optional note) → subsequent WDD documents/AutoStacja imports can attach to this same order via the same identity-lookup logic used by the automatic path.

**Operational lifecycle:** search (order number primary, VIN secondary) → detail view (Nagłówek / Pozycje / Magazyn i Zam. / Załączniki, comments in pilot) → warehouse tab reads live `inventory_balances`/movement history filtered by reference; orders/receipts tab reads `repair_order_source_documents` + associated movement headers grouped by document → advisor or manage-permission user can edit header fields, close/reopen → manage-identity-permission user can correct business-identity fields via the dedicated audited RPC → archive requires explicit archive permission, never a plain field edit.

### Proposed domain model

All names below are **proposed, not final** — subject to normal code-review naming conventions at implementation time. All tables: `id uuid PK default gen_random_uuid()`, `organization_id uuid NOT NULL`, `branch_id uuid NOT NULL` (branch required per §24), `created_at`/`updated_at timestamptz`, `deleted_at timestamptz` only where soft-delete is meaningful (most of these use status-based archival instead, per §40).

- **`repair_orders`** — `order_number text NOT NULL`, `order_year smallint NOT NULL`, `workshop_code text NULL` (deferred field, populated only once/if future parser work lands — see §4/§5), `vin text NULL` (indexed, not unique), `brand text NULL`, `dealer_name text NULL`, `advisor_user_id uuid NULL REFERENCES public.users(id)` (per §8 recommendation (a)), `status text NOT NULL DEFAULT 'open' CHECK (status IN ('open','closed','archived'))`, `source_type text NOT NULL CHECK (source_type IN ('matcher','manual'))`, `created_by uuid NOT NULL REFERENCES public.users(id)`, `updated_by uuid NULL`, `closed_at timestamptz NULL`, `closed_by uuid NULL`. Unique constraint (initial, per §4 recommendation (a)): `UNIQUE (organization_id, branch_id, order_number, order_year)` — **not** including `workshop_code` yet, with the collision risk explicitly documented in code comments and product-clarification text, and re-evaluated once/if workshop_code becomes obtainable.
- **`repair_order_lines`** — `repair_order_id uuid NOT NULL REFERENCES repair_orders(id)`, `source_wdd_line_id uuid NULL REFERENCES wdd_matcher_lines(id)` (per §11), `sku text NULL`, `product_name text NULL`, `ordered_quantity numeric NOT NULL`, `unit text NULL`, `variant_id uuid NULL REFERENCES inventory_variants(id)` (resolved via `WarehouseImportResolverService`, tri-state — nullable if unresolved), `note text NULL`. **No `location_id`, no `received_quantity`/`issued_quantity` columns** — those are always read-model projections, never stored (per §12/§13).
- **`repair_order_source_documents`** — `repair_order_id uuid NOT NULL`, `document_type text NOT NULL CHECK (... IN ('wdd','order_addition','autostacja_import'))`, `source_document_number text NULL` (e.g. WDD number), `wdd_matcher_session_id uuid NULL REFERENCES wdd_matcher_sessions(id)`, `wdd_matcher_block_id uuid NULL REFERENCES wdd_matcher_blocks(id)`, `imported_by uuid NOT NULL`, `imported_at timestamptz NOT NULL DEFAULT now()`. Unique constraint to prevent duplicate WDD import: `UNIQUE (organization_id, source_document_number) WHERE document_type = 'wdd' AND source_document_number IS NOT NULL` (per §36).
- **`repair_order_legacy_records`** — `repair_order_id uuid NOT NULL`, `source text NOT NULL DEFAULT 'autostacja'`, `external_reference text NULL`, `record_date date NULL`, `description text NULL`, `inventory_effect text NOT NULL DEFAULT 'none' CHECK (inventory_effect = 'none')` (per §37 — deliberately constrained so it can never accidentally become a real movement), `created_by uuid NOT NULL`.
- **No new table for "domain activity"** — uses `platform_events` (per §39, Repository findings on audit infrastructure). No new table for warehouse-side quantities — uses live `inventory_balances`/`inventory_movement_headers`/`_lines` filtered by `reference_type = 'repair_order'` / `reference_id = repair_orders.id` (header-level reference, matching how movement lines never carry a repair-order FK directly — mirrors §35's "many lines relate to many receipt/issue lines" requirement by never forcing a 1:1 FK anywhere).

### Authorization and ownership model

Proposed permission set, following the exact `<module>.<resource>.<verb>` convention and the Help Desk precedent of a coarse triad (no bespoke `update-own`/`update-all`/`assign` strings, per Verified technical findings):

`module.repairorder.access` (module gate) · `repairorder.orders.read` · `repairorder.orders.create` · `repairorder.orders.manage` (covers header edit-all, close/reopen, assign advisor for non-owners) · `repairorder.orders.archive` (separate from `.manage`, per §9/§40's explicit "archive requires distinct permission") · `repairorder.identity.manage` (the dedicated, rare, privileged business-identity-correction permission, per §23) · `repairorder.legacy_records.manage` (pilot-only, gates §37 legacy-issue-record creation).

RLS pattern (Tier 1, per Verified technical findings): every table `ENABLE ROW LEVEL SECURITY` **and** `FORCE ROW LEVEL SECURITY`. `SELECT`: `is_org_member(organization_id) AND has_branch_permission(organization_id, branch_id, 'repairorder.orders.read')`. `INSERT`: same shape with `.create`. `UPDATE` on `repair_orders`: `has_branch_permission(...,'repairorder.orders.manage') OR (advisor_user_id = auth.uid() AND has_branch_permission(...,'repairorder.orders.read'))` — mirroring the Help Desk creator-or-manager shape but keyed on `advisor_user_id` instead of `created_by`, satisfying §7/§26 (ownership grants header edits, never bypasses the permission system — a user with no read permission at all still cannot edit even if listed as advisor, since the branch-permission check is `AND`ed, not substituted). `DELETE`: `USING (false)` on every table (hard delete forbidden, per §40 — matches `inventory_movement_headers`'s exact pattern). Identity-correction fields (`order_number`, `order_year`, `workshop_code`, `branch_id`) are **not** covered by the general `UPDATE` policy at all — they can only change through the dedicated `repairorder_correct_identity` SECURITY DEFINER RPC (checking `repairorder.identity.manage`), never via a plain table UPDATE, enforced by excluding those columns from the general policy's `WITH CHECK` or (cleaner) via a `BEFORE UPDATE` trigger that raises if those columns changed outside the RPC's session-local flag.

`can_access_comment_target` gets a fourth `IF p_target_type = 'workshop.repair_order' THEN ... END IF` branch (new migration, full-body `CREATE OR REPLACE`, per the exact pattern of the three existing branches) — structured like the `helpdesk.ticket` branch (creator/advisor-or-manager EXISTS check), not the flatter `planning.task` branch, since RepairOrder needs per-row advisor ownership, not just a flat permission check.

### Architecture implications

- RepairOrder introduces **no new architectural pattern** — every piece (reference-based movement linkage, generic attachments/comments via target registry, `platform_events` for audit, `WarehouseImportResolverService` for catalog mapping, `MovementImportSourceAdapter` for future file import, `SECURITY DEFINER` RPCs for privileged state transitions) already exists and is proven elsewhere in this codebase. This is a **composition** task, not a greenfield-architecture task, despite the domain tables themselves being new.
- The one genuinely new piece of infrastructure is the **Matcher approval action** (§18 recommendation (b)) — small, scoped, and arguably overdue independent of RepairOrder.
- The reservation/allocation and container systems remain intentionally **unwired** for the pitch/initial-pilot scope of this plan — RepairOrder's reference-pattern compatibility with them is a design property, not a Phase-1 deliverable.
- The severe migration-tree drift (Repository vs live-schema drift, above) is an **external risk to this plan's Phase 2**, not something Zone 3 caused or can fix by itself — it must be surfaced to whoever owns migration/deployment tooling before the first Zone 3 migration is applied for real.
