## Decisions discovered during implementation

### DISCOVERY-001 — Applied migrations got live-tracked under different version numbers than their local filenames (self-caught, corrected same session)

- **Issue**: `mcp__supabase-target__apply_migration` records the live `schema_migrations` version as the timestamp _at the moment it's applied_, not the timestamp embedded in the `name` parameter passed to the tool. The Phase 2/status/pgtap migrations were locally named with timestamps `20260910120000`/`20260910130000`/`20260910140000`, but were live-tracked as `20260910061711`/`20260910071755`/`20260910071815`. This is exactly the class of drift found and documented in Phase 0A (`03-repair-orders-phase0a-baseline.md`) — reproduced here in miniature within the same session, which is itself a useful confirmation of that finding's mechanism.
- **Evidence**: `mcp__supabase-target__list_migrations` post-apply.
- **Resolution**: local files renamed to match the actual live-applied version numbers; a missing local file for the pgtap-enable migration was created; all cross-references (migration header comments, the pgTAP test file, the implementation plan, the domain types file's doc comment) updated to the corrected filenames. No further product-owner approval needed — this is a same-session self-correction of the "local migration matches what MCP applied" discipline the work order requires, not a design question.
- **Takeaway for future phases**: always run `list_migrations` immediately after `apply_migration` and name the local file after the _live-reported_ version, never the version guessed at write-time.

### DISCOVERY-002 — `user_effective_permissions` compiled cache does not auto-refresh when new permission rows are added to a wildcard's namespace

- **Issue**: `has_branch_permission`/`has_permission` read from `public.user_effective_permissions`, a cache populated by `compile_user_permissions()` and refreshed only by triggers on `role_permissions`/`user_role_assignments`/`organization_members`/`user_permission_overrides`. Inserting new rows into the `public.permissions` catalog (e.g. Phase 2's `workshop.repair_orders.read/manage_own/manage_all`) does **not** fire any of those triggers. Result: every user who already held the `workshop.*` wildcard (or any concrete `workshop.*` permission) before the Zone 3 migration had a stale cache lacking the 3 new slugs — LIVE VERIFIED with a real org_owner user (`has_branch_permission(..., 'workshop.repair_orders.manage_own')` returned `false` despite the user holding `workshop.*`).
- **Evidence**: `user_effective_permissions` query before/after; `has_branch_permission` call before/after.
- **Resolution**: one-time backfill migration (`20260910080123_recompile_workshop_wildcard_holders_for_repair_orders.sql`) calling the existing `compile_user_permissions(user_id, organization_id)` for every `(user_id, organization_id)` pair whose cache already contained a `workshop.%` entry. Verified fixed live.
- **Broader implication, not fixed here (out of scope)**: this same gap likely applies to _every_ prior module's migration that added a new concrete permission under an already-wildcard-granted prefix (e.g. `helpdesk_module.sql`, `analytics_module.sql` if either ever added permissions after initial seeding) — none of those were touched this session; flagged here as a candidate repo-wide follow-up, not assumed to need action.

### DISCOVERY-003 — `inventory_finalize_posting` (existing RPC) trusts `p_actor_user_id` with no authorization check, and is EXECUTE-granted to `anon`

- **Issue**: LIVE VERIFIED via `pg_get_functiondef` — `inventory_finalize_posting(p_movement_id, p_actor_user_id)` performs zero `has_permission`/`has_branch_permission` check and never validates `p_actor_user_id = auth.uid()`; it stamps `posted_by`/`actor_user_id` in an audit log directly from the trusted parameter. `has_function_privilege` confirms `EXECUTE` is granted to both `anon` and `authenticated` (default grant, never revoked). This is a real, pre-existing privilege-escalation / audit-log-forgery surface, unrelated to Zone 3.
- **Evidence**: `pg_get_functiondef`, `has_function_privilege` queries this session.
- **Resolution**: **not fixed** — explicitly out of scope for this session (Inventory domain, not Zone 3). The new Zone 3 RPC (`materialize_repair_orders_from_session`) deliberately does NOT copy this pattern (see Phase 3 notes above: verifies `p_actor_user_id = auth.uid()`, checks `has_branch_permission` itself, EXECUTE revoked from `anon`/`PUBLIC`).
- **Recommendation**: flag `inventory_finalize_posting` (and worth auditing `inventory_create_draft` and any other `p_actor_user_id`-taking RPC) for a dedicated security-hardening pass — outside Zone 3's scope, reported here rather than silently left undocumented.

### DISCOVERY-004 — Workshop RepairOrder list does not auto-refresh on active-branch switch (Zone-1-owned, surfaced by manual UAT 2026-09-11)

- **Issue**: switching the active branch in the app does not immediately refresh/invalidate the Workshop RepairOrder list (`/dashboard/workshop`) — the previous branch's RepairOrders remain visible until a manual page reload. Surfaced during the product owner's 2026-09-11 manual browser UAT, not by any automated test.
- **Evidence**: product-owner manual UAT — switching branches leaves the prior branch's orders visible until reload; after a manual reload, the correct branch-scoped data is shown and no cross-branch data remains accessible; returning to the original branch afterward correctly restores its RepairOrders.
- **Why this is Zone-1-owned, not a Zone 3 gap**: the Workshop list page is a Zone 3 consumer of the active-branch context, not the owner of branch-switch propagation/cache-invalidation — that mechanism is cross-cutting app infrastructure. No RLS/security boundary is crossed (the underlying query is still correctly branch-scoped and RLS-enforced; this is purely a client-side cache/refresh timing gap, confirmed safe by the reload always showing correct data with no leakage). This matches the shape of other branch-context propagation concerns that belong to Zone 1's auth/org/branch-access work, not to an individual module's list page.
- **Resolution**: **not fixed in this pass** — explicitly deferred to Zone 1 work, per product-owner instruction. Recorded here for traceability rather than silently patched locally in Zone 3 (which risks diverging from however Zone 1 ultimately solves branch-switch cache invalidation app-wide).
- **Not a Phase 6 blocker**: Phase 6's own acceptance criteria (findability by search, correct RLS-scoping) are unaffected — verified both live and via manual UAT. This is recorded as a known, non-blocking follow-up issue.

### DISCOVERY-005 — `repair_orders_update`'s ownership-check subquery was silently defeated by `crm_contacts`' own RLS for any actor without `crm.contacts.read` (CONFIRMED LIVE BUG, found and fixed in Phase 7, pre-existing since Phase 2)

- **Issue**: the RLS ownership check `advisor_contact_id IN (SELECT id FROM crm_contacts WHERE linked_user_id = auth.uid())` is a plain correlated subquery under the querying role's own privileges — unlike `has_branch_permission` (SECURITY DEFINER, reads `user_effective_permissions` directly, bypassing its RLS), this subquery is itself subject to `crm_contacts_select`'s own policy, which additionally requires `crm.contacts.read`. Any `manage_own` RepairOrder advisor who does not separately hold `crm.contacts.read` — a realistic role split, since Workshop and CRM are different modules — had their own genuine ownership silently evaluate to false on every UPDATE attempt: a hard self-lockout on the exact ownership model this table's RLS exists to enforce. This has been live since Phase 2's original migration (`20260910061711_repair_orders_core_schema.sql`); it was not caught by Phase 2's own pgTAP suite because that suite tests policy _wording_, not full authenticated-session behavior (explicitly documented as a scope note in that suite's own header).
- **Evidence**: LIVE VERIFIED this session while writing `093_repair_orders_header_ownership_rls_test.sql` — a real self-linked `crm_contacts` row, visible when queried as `postgres`, returned zero rows from the identical subquery run as the genuinely-RLS-enforced `authenticated` role holding only `workshop.repair_orders.manage_own`/`.read` (no `crm.contacts.read`).
- **Resolution**: `is_own_advisor_contact(p_contact_id uuid) RETURNS boolean SECURITY DEFINER` (matches `has_branch_permission`'s own established bypass-the-underlying-table's-RLS pattern), migration `20260911172434_repair_orders_advisor_self_check_fn.sql`, live-applied. `repair_orders_update` and `repair_orders_insert` rewritten to call it instead of the raw subquery. Re-verified fixed live: the same self-linked-contact scenario now correctly succeeds.
- **Takeaway for future phases**: any RLS policy that needs to check "does row X relate to a row in table Y that the current user owns/is linked to" must NOT express that as a plain subquery against Y if Y has its own RLS that could plausibly exclude the current caller — use a SECURITY DEFINER helper, the same way `has_branch_permission` already does for the permission-cache case. Worth a repo-wide grep for the same pattern elsewhere (not performed this session — out of Zone 3's scope to audit other modules).

### DISCOVERY-006 — Advisor "employee-role" picker scoping is schema-unimplementable as literally described; an open product decision, not silently resolved

- **Issue**: the architecture doc's own prose ("a `crm_contacts` row representing an internal advisor gets a `crm_party_roles` row with `role='employee'`") cannot be implemented literally — `crm_party_roles.role` is a PARTY-level tag (`crm_party_roles.party_id -> crm_parties.id`), and `crm_party_roles` has no `contact_id` column at all. A CONTACT only relates to a PARTY via the separate `crm_party_contacts` junction table. Tagging a specific person-contact as "employee" via this mechanism would require creating a synthetic "staff" `crm_parties` row with `role='employee'`, then linking each advisor's `crm_contacts` row to it via `crm_party_contacts` — an entirely new, undecided, unprecedented pattern (a repo-wide grep for `employee` found no existing usage of this scheme anywhere, only an unrelated auth-role label in `UserRoleManager.tsx`).
- **Resolution this session**: NOT invented around. `RepairOrdersService.listAdvisorCandidates` uses an interim, schema-real, reversible signal instead — `crm_contacts` rows already linked to a real platform user (`linked_user_id IS NOT NULL`), since those are the only contacts that can ever function as an "owner" under the `manage_own` RLS model regardless of any party-role tagging. This is a UI-scoping convenience only, not a security boundary (RLS enforces real ownership independent of picker scoping).
- **Decision needed from the product owner, not closeable without one**: (a) accept the `linked_user_id`-based interim scoping as sufficient long-term, or (b) explicitly design the synthetic-party-per-employee (or an alternative) mechanism the architecture doc's prose implied. Not a Phase 7 blocker — recorded for whenever this is picked up.
