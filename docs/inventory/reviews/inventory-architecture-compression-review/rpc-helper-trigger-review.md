### CRITICAL FINDING — live, currently exploitable, not previously escalated

**`ambra.inventory_movement_engine` is still used as a bare
authorization signal on `inventory_balances` and `inventory_settings`,
the exact anti-pattern IC-7 explicitly redesigned away for the
posted-header trigger.** IC-7's own NULL-comparison fail-open fix
(`security-evidence.md` item 3) closed only the _accidental_ variant
(GUC never touched) for these two tables. It did **not** close the
_deliberate_-set variant — unlike the header/line triggers, which now
validate the substance of a change, these two triggers still do only:

```sql
-- inventory_guard_balance_write() — live body, confirmed
IF COALESCE(current_setting('ambra.inventory_movement_engine', true), 'off') <> 'on' THEN
  RAISE EXCEPTION 'inventory_balances can only be changed by the movement engine';
END IF;
RETURN NEW;  -- if GUC='on', ANY change is allowed, unconditionally
```

Live-queried RLS on `inventory_balances`/`inventory_settings` confirms
both `UPDATE` policies impose no column/value restriction beyond
holding `warehouse.inventory.operate`/`.adjust`/`.reverse`. So today,
any ordinary operate-permissioned user can run:

```sql
SELECT set_config('ambra.inventory_movement_engine', 'on', true);
UPDATE inventory_balances SET on_hand_quantity = 999999 WHERE ...;
```

and silently corrupt the physical stock truth — no ledger entry, no
audit log, none of IC-1's invariant checks (e.g. the "would strand
committed stock" guard), completely untraceable. The settings trigger
has the same shape: setting the GUC bypasses the `warehouse.settings.
manage` permission check entirely, letting an ordinary operate-holder
(not a settings manager) edit organization inventory settings.

No test in the 110/111 pgTAP suites exercises "deliberately set the
GUC, then raw-write balances/settings with an out-of-invariant value" —
every balances/settings test proves only the _never-touched-the-GUC_
case now fails closed. `inventory-core-architecture.md` §9D marks this
"explicitly NOT touched, already a disclosed IC-7 item" — live evidence
shows it was never actually closed for these two tables.

**This directly contradicts the frozen accepted fact "raw writes are
closed."** Per the compression-review task's own instruction to flag a
direct contradiction to a frozen fact, this is recorded here as a
**required pre-IC-8 correctness item**, not a "fewer mechanisms"
recommendation — this audit does not implement a fix (audit-only
scope), but the recommended shape (for a future pass) is the same
substance-validation redesign IC-7 already proved works for the header
trigger: the GUC itself should be **kept** for orchestration (every
legitimate writer already sets it), but the two reader triggers must
stop treating `GUC='on'` as _sufficient_ — they need either a
substance/delta check or a structural signal that isn't self-settable
by an ordinary session.
