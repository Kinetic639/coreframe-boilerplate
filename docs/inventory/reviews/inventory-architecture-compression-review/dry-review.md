## Valuation snapshot defect disposition

**Real caller chain — confirmed dead-end plumbing, not active**:
`createInventoryValuationSnapshotAction` (`app/actions/warehouse/
inventory/index.ts:2954`) has **zero UI/component callers anywhere** —
no page, button, or export in `apps/web/src/app`/`components` matches
`valuation`/`Valuation`. The action → `InventoryEnterpriseService.
createValuationSnapshot` → `inventory_create_valuation_snapshot` chain
is real, callable, and permission-checked, but structurally unreachable
from the product today. `inventory_valuation_snapshots` has 0 rows
live and no other TS reader.

**Was `inventory_balance_analytics` ever real?** Yes — created as a
view in `20260508090000_inventory_phase3_advanced_features.sql:622-679`
(joins balances→variants→products, LEFT JOINs settings/variant_costs,
2 LATERAL last-receipt/last-issue subqueries), later altered for
`security_invoker=true`. **No DROP of this view exists anywhere in
either migration tree** — yet live `to_regclass(...)` returns NULL on
`supabase-target`. Conclusion: the view was defined in a tracked
migration but was never actually applied to (or was lost from) the
live database — a migration/database-drift bug, not a "feature removed
on purpose" story. Diagnosing WHY it never applied is infrastructure
work outside a read-only audit's scope, but it is worth flagging
explicitly as unusual (suggests a rebase/reset of the target branch at
some point, or a silently failed migration).

**Current correct data source**: `inventory_balances` already carries
the raw columns needed (including a real generated `available_
quantity` column); `inventory_stock_ledger_entries` has the movement-
level detail the missing view's own LATERAL subqueries used. No
successor view already exists (`%valuation%`/`%balance%`/`%analytics%`
in `public`: zero rows). A fix would either recreate the original view
or inline-rewrite the snapshot RPC's own query against current tables.

**Recommendation: DEFER.** Reasoning: (1) not actively used — zero UI
entry point, zero table readers, 0 rows, not urgent/customer-facing;
(2) not dead-enough to just REMOVE either — the properly-indexed,
constrained `inventory_valuation_snapshots` table and the `"valuation"`
export-type enum entry suggest a genuinely planned feature, not
abandoned mid-thought; removing the function means redoing this work
from scratch later; (3) FIX/REBUILD are both reasonable but unjustified
effort right now given zero reachable usage. **Explicit pre-IC-8
backlog item**: recreate `inventory_balance_analytics` (or, the leaner
option, inline-rewrite the snapshot query directly against `inventory_
balances`/`inventory_variant_costs` — it was only ever consumed by this
one function) AND build the missing UI entry point as one combined
piece of work — fixing only the SQL would just recreate today's dead-
end-plumbing problem with a working backend underneath.

## DRY review — genuine duplicate business rules only

Only flagged where the SAME business rule is independently implemented
in 2+ places, could silently drift, and duplication isn't merely
similar-looking code implementing conceptually separate rules.

| **Actor-identity check** (`p_actor_user_id IS NULL OR IS DISTINCT FROM auth.uid()`)                             | Textually yes (38 files, byte-identical string), but **not a real DRY violation**                                                                         | **Leave alone.** A security check gating every `SECURITY DEFINER` function must be inline and trivially auditable per-function by anyone reading that one function's own `pg_get_functiondef` — a shared helper would mean an auditor must also trust a separate, un-inlined definition hasn't drifted, a strictly worse security-review property for a one-line check. Minor non-urgent note: 3 of the earliest container-RPC migrations lack the explicit `IS NULL OR` guard (though `IS DISTINCT FROM` already treats NULL as distinct, so practical behavior is very likely equivalent) — worth a non-urgent consistency pass, not a bug.                                                                                                                                                                                                                                                                                                                                                                                       |

| **Document numbering generation** (lock `inventory_settings` row, read+format prefix+padded-counter, increment) | **YES — genuine DRY violation**                                                                                                                           | Independently re-implemented for 6+ document types across 10 call sites (movement/draft/reservation/allocation/purchase-order/branch-transfer numbering). Every site hand-rolls the identical 3-step shape. A real "could silently drift" risk: if the numbering rule ever changes (per-branch series, gap-avoidance, different padding), each of the ~10 sites needs the identical edit independently applied, and it is easy to miss one. **Should centralize** — e.g. a single `inventory_next_document_number(org, counter, prefix)` helper. | **Idempotency key handling** (check-then-short-circuit before mutating)                                         | **YES — genuine DRY violation, with proof it already drifted once**                                                                                       | 12 files hand-roll the same shape. **Direct evidence of drift**: a dedicated fix migration documents a real, previously-shipped bug where `inventory_receive_purchase_order` mutated `received_quantity` BEFORE checking the idempotency key, so a retry under the same key double-incremented `received_quantity` even though the physical movement itself deduplicated correctly. One authoritative implementation, two callers — the correct shape.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Movement-line validation**                                                                                    | No obvious duplication                                                                                                                                    | Effect-application logic lives in exactly one place (`inventory_finalize_posting_internal`); reversal reuses it via the same function call chain.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Priority read for a future pass**: the idempotency-ordering audit
(re-check ~10 sites for the exact bug class already fixed once) is the
single highest-value, lowest-risk DRY follow-up found in this entire
review — it is a correctness-hardening pass over already-known-good
code, not a redesign.
